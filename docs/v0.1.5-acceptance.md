# Nexus v0.1.5 release acceptance

This document is the canonical release gate for Nexus v0.1.5. The implementation plans and test
catalogs describe how work is performed; this document decides whether the candidate may ship.

Every item marked **required** is non-waivable. A skipped, refused, flaky, or partially exercised
required check is a failure. Evidence must come from one immutable candidate revision and its packed
artifacts. Rebuilding after a failure creates a new candidate and invalidates the previous evidence.

## Candidate and isolation

### A1. Candidate identity — required

- The source revision, native binary hash, npm tarball hashes, container image digest, dirty-path
  hashes, toolchain versions, resource limits, and redacted environment are recorded in one manifest.
- `nexus --version`, every Cargo package version, and all three npm package versions report `0.1.5`.
- The packed packages are exactly `@egregore/nexus`, `@egregore/nexus-cli`, and
  `@egregore/nexus-gateway`. The umbrella package installs the native CLI, Gateway, and Webconsole
  assets appropriate for the current operating system without compiling user harnesses.

### A2. Host isolation — required

- Validation runs in exactly one disposable Docker validator capped at 6 CPUs, 8 GiB of memory, and
  1,024 PIDs. It does not mount the host Nexus home or Lens session data.
- Before/after evidence proves that the host daemon, Gateway, Webconsole, IPC socket, listeners,
  discovery files, and databases were not changed or replaced.
- The validator uses its own home, databases, ports, process tree, harness workspaces, and PACTBIN2
  fixtures. No validation command installs, restarts, attaches to, or signals a host Nexus process.

## Identity and lifecycle

### B1. Stable identity — required

- Agent IDs are the canonical internal address. Names are unique mutable aliases; renaming to an
  occupied name fails without changing either identity.
- All DM, thread, queue, attach, revive, REST, and WebSocket target resolution accepts a stable
  agent ID. A valid agent ID wins over a stale display name. Project metadata never changes routing.
- Renaming an agent cannot wedge its write path. A valid immutable client key remains authoritative
  across rename, reconnect, and daemon restart.
- Humans and agents remain distinct principals. Humans are not revival targets and are never
  materialized as agent runtimes.

### B2. Restart reconciliation — required

- Two consecutive daemon restarts and two consecutive Gateway restarts restore complete canonical
  identity/runtime descriptors exactly once.
- Gateway rosters converge to daemon truth without refresh. Missing agents are
  restored and stale pre-boot rows are retired.
- Existing human cookies rebind their stable human principal before the first accepted write in a
  new daemon boot. Unknown cookies fail before durable acceptance.

### B3. Human Webconsole attribution — deferred

Webconsole-specific attribution and browser rendering are not v0.1.5 release gates. Human caller
authority on Nexus mutations remains covered by the Gateway contracts and the required Lens
LP1–LP16 ocular client. The dedicated Webconsole matrix will return in a later release.

## Gateway and WebSocket contracts

### C1. Browser mutation security — required

- Cookie-authenticated HTTP mutations require the issued readable CSRF proof. Caller-supplied proof
  is replaced, not trusted.
- Writable browser WebSockets derive proof only from one exact cookie/subprotocol pair. Forged
  headers, query fields, frame fields, missing proof, mismatched proof, and duplicate proof are
  rejected before enqueue.
- The same centralized guard protects source mode, packed HTTP dispatch, and packed WebSocket
  dispatch. Bearer-only and explicit cookie-free local operation retain their documented behavior.

### C2. Developer-event WebSocket — required

- A real authenticated upgrade receives `subscribe.ack`, then live thread, DM, roster, and fleet
  events in canonical order.
- Thread and DM events originate from Gateway's post-commit canonical projection/change bus. After
  initial hydration, delivery is push-driven: no periodic `developerEventsSource.since()` polling.
- Reconnect supports bounded replay by cursor, duplicate suppression, explicit gap/resync, boot-aware
  cursor reset, topic isolation, concurrent subscribers, and typed 1013 backpressure recovery.
- Gateway-only and daemon-only restarts recover the subscription without UI reload or silent loss.

### C3. Agent-session WebSocket — required

- Restored sessions materialize by stable agent ID/session ID and open with a canonical non-null
  session ID. Two concurrent lanes cannot cross-route input or events.
- Input receipt, run start, text/tool deltas, run finish, queued input, steer, interrupt, and compact
  preserve attribution, correlation, order, and exactly-once execution.
- Reload/reconnect and daemon/Gateway restart resume from the last accepted cursor without missing or
  duplicate transcript rows. Slow readers and full queues have bounded, typed recovery.

### C4. REST/WebSocket agreement — required

- Name and agent-ID reads resolve to the same current target. REST hydration and subsequent
  WebSocket deltas produce one canonical history without duplicate or stale rows.
- Subscription errors and gaps are visible to clients and force recovery; a reader cannot remain
  falsely marked live after an error.

## Packed CLI and Gateway

### D1. Clean packed install — required

- The npm tarballs install into an empty prefix and run from a foreign working directory without a
  source checkout, `NODE_PATH`, inherited Nexus state, or source/tsx fallback.
- Only `@egregore/nexus` is installed at the prefix top level; `@egregore/nexus-cli` and
  `@egregore/nexus-gateway` remain nested dependencies, and all three launchers resolve through the
  umbrella package rather than colliding top-level bins.
- Every dynamic Gateway/WebSocket import is present in the packed artifact. The shipped binary, not
  a source helper, passes health, auth, thread replay/live wake, agent-session relay, and bounded
  shutdown checks.

### D2–D3. Webconsole CLI and WebUI browser behavior — deferred

The Webconsole lifecycle matrix, W1–W8 browser cases, D2 detached result, and D3 aggregate are not
v0.1.5 release requirements. Their existing implementation and tests remain preserved for a later
release, but default/`--all`, final assembly, validation, and soak do not invoke or require them.

## Lens ocular client

### E1. PACTBIN2 session-store product validation — deferred

Lens may use its normal PACTBIN2 runtime dependency during ocular validation, but PACTBIN2
persistence, damage handling, and the E1 aggregate are separate product gates and cannot block the
Nexus v0.1.5 release.

### E2. Human-path Lens ocular gate — required

- A documented live-plugin command loads `plugins/lens.nexus` against only the isolated candidate
  Nexus. It proves health and authentication, history and queue hydration, thread compose/reply,
  two-way DM, agent-session prompt and progressive output, queued send, steer, interrupt/cancel,
  compact, reload hydration, Gateway and daemon reconnect, and visible typed auth, offline, and
  queue-authority failure recovery. Every mutation is durably attributed to the human caller while
  the selected agent remains target only. The command refuses host Nexus/Lens state and retains
  candidate-bound evidence; unit, mocked, direct-store, or source-only substitutes do not satisfy
  this check.
- Gateway auto-detection remains the default. The visible Lens affordance may select a manual
  HTTP(S) Gateway URL only after a successful health probe; a healthy manual choice overrides
  discovery, an unhealthy saved choice falls through to discovery, and Auto-detect clears the
  override. The live-plugin gate configures the candidate through this visible affordance.
- Release evidence runs the built Electron renderer in production mode from the candidate-bound
  staged application tree. No Vite process, dev-server URL, or port 1422 may be present in the
  packed validator; Vite is permitted only for explicitly source-mode development runs.
- LP1–LP16 execute against the real Electron renderer through visible controls. Direct store calls,
  renderer bridges, or hidden internal invocation cannot satisfy an ocular check.
- Every surface sourcing agent, Gateway, event-WebSocket, or agent-session-WebSocket data has a
  visible input/output assertion and a failure-state assertion.
- Screenshots, DOM snapshots, bounded process logs, health probes, and run/readiness/candidate-bound
  mutation attribution are retained for the LP surfaces.

## Real harnesses, hooks, and endurance

### F1. Live Codex and Claude — required

- The packed candidate launches genuine installed Codex and Claude harnesses inside the validator.
  Nexus uses the user's existing harness binaries; it does not compile or modify them.
- Both agents pass roster, DM in both directions, thread post/live event, session observe/input,
  progressive output, queued input/steer, reconnect/replay, and exactly-once delivery checks.
- Harness unavailability or exhausted external credits is reported distinctly. It cannot be counted
  as a Nexus pass, but it also cannot be disguised as a Nexus defect.

### F2. Message hooks — required

- Shell, JavaScript, and Python local hook fixtures exercise `before_send` and `after_receipt`, text
  and metadata mutation, signed execution provenance, and failure handling.
- `interrupt`, `yield_turn`, and `after_tool_loop` timing execute at their documented message
  boundaries. Hooks never intercept the harness token stream and disabled hooks preserve baseline
  delivery behavior.

### F3. Restart soak — required

- The exact packed candidate completes a 30-minute dual-WebSocket soak under the 6-CPU cap with
  live thread/DM traffic, agent-session traffic, repeated independent daemon/Gateway reconnects, and
  Lens observation.
- Each planned restart proves the intended daemon boot ID/PID or Gateway PID/instance changed while
  the other authority stayed stable. Accepted traffic straddles each disconnect and replays from the
  last accepted cursor without loss or duplication; Codex and Claude each produce a correlated run,
  progressive assistant marker, and matching terminal event.
- Thirty-second checkpoints record advancing per-topic and per-agent cursors, replay/resync counts,
  exact 6-CPU/8-GiB/1,024-PID cgroup limits, RSS/CPU/file-descriptor/task/socket counts, queue and
  backpressure state, subscriber/reader counts, renderer responsiveness, and bounded memory/disk
  trends. Required diagnostics and final process/listener topology fail closed.
- The soak has no dead letters, lost or duplicate accepted messages, cross-route delivery, silent
  subscription failure, offline restored participant, identity drift, queue wedge, crash loop, or
  unbounded memory/disk growth.

## Evidence and release decision

### G1. Required evidence

The evidence bundle contains:

- candidate and isolation manifests plus before/after host snapshots;
- focused and full Rust, Gateway, package, Lens ocular-client, and hook test reports;
- packed-file inventory and clean-prefix install logs;
- redacted HTTP upgrades and WebSocket subscribe/ack/event/gap/1013/reconnect frames;
- canonical attribution rows and cursor checkpoints;
- Lens LP1–LP16 ocular artifacts; and
- soak metrics, bounded logs, disk growth, and final process/listener snapshots.

All producers use the same run ID and readiness digest. Candidate manifests, receipts, case metadata,
artifact inventories, and detached seals are no-follow, single-link, mode/owner checked, content hashed,
and atomically published under the canonical lab evidence root. Partial, stale, cross-run, synthetic,
refused, skipped, or unbound evidence is a failure.

### G2. Ship rule

v0.1.5 may be tagged or published only when every required section above is green for the same
candidate, the tracked worktree contains no unintended release change, and review has no unresolved
release blocker. A manual demonstration, unit-only substitute for a real-network check, or a pass
from an older candidate does not satisfy this contract.
